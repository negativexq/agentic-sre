# v0.3 experiment sequence

Status: design-only. No v0.3 runtime or live experiment is implemented by this
document.

## Sequence

```text
A0  Frozen v0.2.0 single-agent baseline
        |
        | representation, topology, protocol and audit improvements
        v
A1  Improved single-agent causal investigation (CONTROL ARM)
        |
        | one independent causal-challenge role, if justified by A1 evidence
        v
A2  Investigator + Critic (TREATMENT)
```

The A1–A0 comparison isolates the effect of explicit component semantics,
production topology, structured causal output, and improved observability while
keeping one model role. The A2–A1 comparison isolates the incremental effect of
independent critique. A2 is not implemented or selected as the A1 architecture.

## A1 research question

> Can the existing bounded single investigator improve causal exploration and
> causal diagnosis when given explicit production topology, canonical component
> identities, structured causal outputs, and better benchmark observability,
> without adding another model role?

## A1 H0 / H1

**H1-A1:** A single bounded investigator with explicit component semantics,
production topology, structured causal output, and auditable investigation
telemetry will improve causal exploration and causal evidence acquisition over
v0.2.0 while preserving evidence authority and zero-write safety.

**H0-A1:** These representation, context, and protocol improvements do not
materially improve causal investigation over the frozen v0.2.0 single-agent
baseline.

## Evidence carried from v0.2

PROVEN observations:

- 66/66 target-bearing tool requests stayed inside alert scope.
- All ten scenarios used all three model calls.
- V020-008 ended with `AGENT_STOPPED` / `insufficient_evidence`.
- V020-010 did not request available change-intelligence tools.
- Six scenarios failed exact free-text service equality.
- Complete final hypothesis payloads were not persisted.

SUPPORTED interpretations:

- V020-003 demonstrates a cross-component exploration gap: alert scope was
  `order-service`, the frozen causal component was `payment-service`, and no
  outside-scope request was persisted.
- V020-010 demonstrates an evidence-acquisition/search-policy gap for the
  available configuration-change surface.

The semantic causes of the six service misses, semantic correctness of trigger
strings, reason for the V020-008 STOP, and any effect of a larger budget remain
UNKNOWN.

## Candidate architecture comparison

| Criterion | A: improved single agent | B: deterministic validator | C: Investigator + Critic | D: specialized agents |
| --- | --- | --- | --- | --- |
| V020-003 cross-component gap | STRONG | MEDIUM | STRONG | STRONG |
| V020-010 change acquisition | STRONG | MEDIUM | STRONG | STRONG |
| Independent measurement | STRONG | STRONG | STRONG | MEDIUM |
| Evidence authority | MANDATORY / preserved | MANDATORY / preserved | MANDATORY / preserved | MANDATORY / preserved |
| Zero-write safety | MANDATORY / preserved | MANDATORY / preserved | MANDATORY / preserved | MANDATORY / preserved |
| Same-budget comparison | STRONG | STRONG | MEDIUM | WEAK |
| Deterministic orchestration | STRONG | STRONG | STRONG | MEDIUM |
| Added complexity | LOW | LOW | MEDIUM | HIGH |
| New failure surface | LOW | MEDIUM | MEDIUM | HIGH |

This is a sequencing matrix, not a post-hoc claim that multi-agent systems are
better. Candidate A is the smallest fair control-arm change and must be
measured before Candidate C is considered. Candidate B can detect selected
protocol defects but cannot establish causal ownership without importing
evaluator truth. Candidate D is not justified by the v0.2 evidence.

## Metric classes

Primary A1 assessment metrics are:

```text
completion_rate
causal_component_accuracy
mechanism_accuracy
structured_trigger_accuracy
ground_truth_causal_component_evidence_rate
evidence_reference_integrity
runtime/tool failure rate
safety gates
```

Diagnostic behavior metrics are deliberately separate:

```text
cross_component_exploration_rate
outside_alert_scope_tool_executions
unique_components_queried
change_evidence_acquisition_rate
STOP rate
components_considered
unnecessary outside-scope exploration rate
```

V020-003 cross-component exploration and V020-010 change-evidence acquisition
are compatibility diagnostics. Neither is a hard scenario-specific release
gate, and A1 must not require a named tool, component traversal or scenario
pass.

## What A1 changes

Only findings-motivated changes are in scope:

1. Separate runtime-owned `WorkloadComponentId` and `DependencyResourceId`
   registries derived from actual topology.
2. Bounded model-visible production topology, without expected answers.
3. Separate `symptom_component` and `causal_component` fields.
4. A controlled structured trigger instead of relying only on free text.
5. Bounded STOP metadata (`considered_components` and
   `missing_evidence_categories`).
6. Per-turn component-target telemetry and outside-alert-scope metrics.
7. Full bounded structured final-hypothesis and evidence-summary persistence.
8. Generic tool-description audit so change tools state their evidence purpose
   and target scope clearly; no scenario-specific tool forcing.

A1 does not add a second model role, hardcode V020-003 or V020-010 behavior, or
change the frozen ten faults.

## Compatibility and generalization sets

The compatibility set is the immutable V020-001 through V020-010 set. Its
purpose is longitudinal comparison with A0, not to serve as the only evidence
for generalization.

The A1 generalization set is currently `PLANNED_NOT_FROZEN`. It will be frozen
before any A1 live model call as a separate evaluator-side artifact. The final
set will contain a modest, feasibility-reviewed number of new real-fault cases
(target range 4–8, final count pending fixture review) covering:

- cross-service dependency failure;
- dependency latency with a different alert surface;
- database resource issues producing service symptoms;
- Kafka/resource issues producing worker symptoms;
- configuration regression causing an indirect downstream symptom;
- shared-dependency ambiguity; and
- at least one same-component negative control.

The set must use the same real fault → telemetry → alert → Incident chain,
remain outside model context, and be frozen with a dataset hash before live
execution. It must not be inspected for live performance during tuning. The
compatibility and generalization hashes, combined hash and final scenario count
are separate release metadata.

## Exploration precision and recall

For eligible cases:

```text
cross_component_exploration_recall
  = cases with a valid causal-component observation / cross-component cases

unnecessary_outside_scope_exploration_rate
  = same-component cases with unnecessary outside-scope execution /
    same-component cases
```

The first compatibility denominator is only one case (`0/1` in A0), so it is a
diagnostic and not a broad generalization claim. A1 must report tool executions,
unique targets and evidence volume alongside recall so indiscriminate topology
crawling is not rewarded.

## What remains fixed

The first A1 compatibility run keeps the v0.2 comparison controlled:

- the original V020-001 through V020-010 real-fault dataset and order;
- the real fault → telemetry → Prometheus → Alertmanager → Incident path;
- `gpt-5.6-luna`, `reasoning_effort=none`, where available;
- at most three model calls and eight actual tool executions per incident;
- provider retries, fallback, routing, voting and best-of-N at zero/absent;
- typed read-only tools, authoritative windows, evidence ownership and duplicate
  suppression;
- benchmark setup authority remains separate from agent authority;
- no shell, Kubernetes writes, remediation, MCP, A2A, RAG or vector memory.

The first A1 run is one pass per compatibility scenario. Any post-call change
requires a new experiment version; selective reruns are prohibited.

The same freeze and no-tuning rule applies to the generalization set once it is
frozen. A1 success is judged by preregistered general metrics, never by a named
V020-003 or V020-010 pass condition.

## A2 preregistration boundary

A2 is a later treatment, not an A1 implementation. It may add one bounded
independent Critic only after A1 is frozen and measured. A2 must inherit A1's
component schema, topology projection, tools, prompt, faults, dataset, grader,
budgets and artifact schema. Its only intended treatment variable is causal
challenge. A2 is conditional: if A1 exposes remaining synthesis or unsupported
attribution failures, a Critic may be tested against A1.

See [the A1 architecture](./v0.3.0-investigation-architecture.md), [the
implementation-independent experiment contract](../benchmarks/v0.3.0-experiment-contract.json),
and [the detailed experiment design](./causal-investigation-experiment.md).
