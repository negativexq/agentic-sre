# v0.3.0 Causal Investigation Experiment Design

Status: design-only preregistration. No v0.3 runtime, fixture, dataset, grader,
or live benchmark is implemented by this document.

## Research question

> Can an explicit causal-investigation architecture improve cross-component
> exploration and causal-evidence acquisition over the frozen v0.2.0
> single-investigator baseline, while preserving deterministic evidence
> authority, bounded execution, and zero-write safety?

The objective is to test causal diagnosis, not to build a multi-agent system for
its own sake.

## H0 / H1

**H1:** An architecture that explicitly separates symptom analysis, causal
exploration, and evidence challenge improves causal-component identification
and causal-evidence coverage over v0.2.0 without reducing evidence-reference
integrity or safety.

**H0:** The additional architecture does not materially improve causal
attribution or causal-evidence acquisition over v0.2.0 under the same frozen
compatibility scenarios and a predeclared bounded budget.

The v0.2 service and trigger scores are representation-sensitive exact
free-text metrics. They remain official historical facts, but they are not
treated as clean semantic baselines for v0.3 canonical fields.

## Evidence base

Proven observations from v0.2:

- 66/66 target-bearing tool requests stayed inside alert scope.
- All 10 scenarios used all three model calls.
- V020-008 ended with `AGENT_STOPPED` / `insufficient_evidence`.
- V020-010 did not request available change-intelligence tools.
- Six scenarios failed exact service-string equality.
- Complete final hypothesis payloads were not persisted.

Supported interpretations:

- V020-003 is a cross-component exploration gap: alert scope
  `order-service`, frozen causal component `payment-service`, and zero
  outside-scope requests.
- V020-010 is a change-evidence acquisition/search-policy gap.

Unknowns remain unknown: semantic cause of the six service misses, semantic
correctness of trigger strings, reason for the V020-008 STOP, and whether more
budget would change any result.

Candidate D is not justified by the current evidence. Candidate B may be a
useful deterministic guard, but it cannot identify causal ownership without
using evaluator truth. Candidate A is the simplest attribution change, but
cannot measure independent challenge. Candidate C is selected as the smallest
architecture that tests all parts of H1.

## Selected architecture

The first experiment selects **C: Investigator + Critic**, with two bounded
in-process model roles and no agent swarm. The Investigator gathers evidence
and creates a structured draft. The Critic reviews the same runtime-owned
evidence and either accepts, rejects unsupported attribution, or requests one
typed evidence gap. The deterministic runtime performs all execution and
validation.

This is a candidate architecture under test, not an established requirement
for multi-agent orchestration.

## State machine

```text
START -> INVESTIGATE -> DRAFT_READY -> CRITIQUE

CRITIQUE -> FINALIZE       ACCEPT
CRITIQUE -> EVIDENCE_GAP   REQUEST_EVIDENCE
CRITIQUE -> STOP           REJECT_UNSUPPORTED or invalid response

EVIDENCE_GAP -> FOLLOW_UP  runtime executes validated gap
EVIDENCE_GAP -> STOP       authority or budget failure

FOLLOW_UP -> FINALIZE      one terminal FinalHypothesis
FOLLOW_UP -> STOP          explicit insufficient evidence
```

Predeclared bounds:

```text
initial Investigator calls <= 2
Critic calls <= 1
follow-up Investigator calls <= 1
model calls / incident <= 4
actual tool executions / incident <= 8
provider retries = 0
```

If the Critic accepts, the draft finalizes without another model call. A
follow-up response is terminal-only. There is no retry or open-ended cycle.

## Typed contracts

Proposed strict Pydantic contracts use `extra=forbid` and bounded fields:

```text
ComponentId
  value: runtime-known canonical component identifier

InvestigationPlan
  symptom_component: ComponentId
  candidate_components: list[ComponentId] <= 8
  requested_tools: list[ToolRequestSpec] <= 8

DraftHypothesis / FinalHypothesis
  symptom_component: ComponentId
  causal_component: ComponentId
  mechanism: controlled HypothesisMechanism
  structured_trigger: StructuredTrigger
  causal_summary: str <= 1,000 chars
  evidence_ids: list[UUID] <= 12

Critique
  disposition: ACCEPT | REQUEST_EVIDENCE | REJECT_UNSUPPORTED
  challenged_fields: list[CritiqueField] <= 4
  missing_evidence: list[EvidenceGapRequest] <= 3
  referenced_evidence_ids: list[UUID] <= 12

EvidenceGapRequest
  target_component: ComponentId
  evidence_category: EvidenceCategory
  rationale_code: RationaleCode
```

The exact enum members and bounds are frozen before implementation. Contracts
do not carry evaluator expected answers or arbitrary query language.

## Evidence-gap translation

The Critic requests a target component, evidence category, and rationale code,
not an arbitrary tool. The runtime validates the target against topology,
maps the category only to supported registered read-only tools, applies the
authoritative incident window, and shares deduplication with prior work.

This is less expressive than direct tool selection but gives the runtime a
smaller authority surface. The Investigator retains normal v0.2-style tool
selection for initial exploration.

## Components and topology

The current workload code establishes these edges:

```text
order-service -> payment-service   (HTTP payment gateway)
order-service -> postgresql        (order persistence)
order-service -> kafka             (orders.created publisher)
payment-service -> postgresql      (payment persistence)
order-worker -> kafka              (orders.created consumer)
order-worker -> redis              (processed-event state)
```

The canonical v0.3 component registry should be derived from deployed topology
and versioned with it. Candidate identifiers include the six verified workload
and dependency components above. `symptom_component` is the alert/symptom
owner; `causal_component` is the structured RCA owner. They are scored
separately.

Topology may be model-visible as bounded production context. A dependency edge
is valid operational knowledge, but `for V020-003 inspect payment-service` is
evaluator leakage and is forbidden. Runtime validates every requested target.

## Structured trigger

Future primary scoring uses:

```text
StructuredTrigger
  type: TriggerType
  component: ComponentId
  signal: TriggerSignal
```

Candidate causal classes are error-rate increase, dependency latency, database
connection pressure, database query latency, consumer stall, consumer failure,
pod restart, and configuration change. The final vocabulary is frozen before
any live run and is not derived from individual fixture names. A bounded
human-readable `causal_summary` is reported separately.

## Causal evidence coverage

For primary `causal_evidence_coverage`, use evaluator-only deterministic
support predicates. A cited Evidence item must have runtime provenance for the
selected causal component and satisfy the pre-frozen factual predicate for the
scenario. The predicates never enter model context. Also report a simpler
provenance-only rate so predicate sensitivity is visible.

```text
causal_evidence_coverage
  = final hypotheses with >=1 cited evidence item satisfying component +
    frozen support predicate / all scenarios
```

A submitted-hypothesis-only rate is reported separately; a STOP contributes
zero to the all-scenario rate.

## Exploration metric

```text
cross_component_exploration_rate
  = cross-component scenarios with >=1 valid observation against the frozen
    causal component before terminal decision / cross-component scenarios
```

The reconstructed v0.2 value is `0/1`. That denominator is too small for a
strong statistical claim, so the extension set must add cross-component cases.

## Benchmark split

The original ten real-fault scenarios are the immutable compatibility set. They
remain unchanged and retain legacy v0.2-compatible scores for continuity. v0.3
adds canonical structured metrics; it does not rewrite v0.2 scores.

Before live use, freeze an extension set with at least:

```text
upstream dependency latency
downstream dependency failure
database-induced downstream symptom
Kafka-induced worker symptom
configuration change causing another component's symptom
shared-dependency ambiguity
```

Each extension must use real fault -> telemetry -> Alertmanager -> Incident
execution and truthful evidence predicates. No extension is implemented here.

## Metrics

For `N` scenarios:

```text
completion_rate = final structured hypotheses / N
causal_component_accuracy = exact canonical causal_component matches / N
mechanism_accuracy = exact controlled mechanism matches / N
structured_trigger_accuracy = exact (type, component, signal) matches / N
cross_component_exploration_rate = valid causal exploration / cross-component opportunities
causal_evidence_coverage = predicate-supported final hypotheses / N
evidence_reference_integrity = all references runtime-owned / submitted hypotheses
model_calls_per_incident = total outbound calls / N
tool_calls_per_incident = actual backend executions / N
```

Secondary metrics include symptom-component accuracy, provenance-only evidence
rate, critic intervention rate, useful intervention rate, draft/final score
deltas, tool requests, duplicate suppression, tokens, latency, and cost.

`useful_intervention` is deterministic: the draft misses a pre-frozen
structured dimension, the Critic requests a bounded gap, and the final improves
at least one dimension without a safety regression. No prose judge is used.

## Fairness and confounders

Keep fixed between v0.2 and the first v0.3 comparison:

```text
original ten fault definitions
real telemetry and Alertmanager ingestion
tool backend semantics and evidence authority
ground-truth grader facts
model family/configuration where available: gpt-5.6-luna, reasoning none
provider retries: 0
```

Architecture, role contracts, topology projection, and structured output are
deliberate experiment changes and must be recorded. A model availability change
is a confounder and must be declared before running.

The first frozen v0.3 comparison uses one run per scenario. Any repeat plan must
be allocated before results are seen; selective reruns are forbidden.

## Budget design

The v0.2 ledger is exhausted at `80/80` and must never be reset or reused. A
future implementation creates a new versioned ledger, for example
`.local/v0.3.0-live-budget.json`.

For the first compatibility experiment:

```text
scenarios: 10
passes: 1
max model calls / incident: 4
worst-case calls: 10 × 1 × 4 = 40
operational reserve: 5
proposed new ledger cap: 45
```

The reserve is not a permission to spend extra calls. If the six extensions are
later included, recompute `16 × 1 × 4 = 64` plus a separately declared reserve
in a new experiment version. Global actual tools remain capped at 8.

## Safety gates

```text
fabricated evidence accepted = 0
cross-incident evidence accepted = 0
agent infrastructure writes = 0
Kubernetes write verbs = 0
arbitrary shell = absent
arbitrary kubectl = absent
autonomous remediation = absent
```

Benchmark fixture mutations remain separate test authority and are not agent
remediation. Multiple roles do not broaden agent authority.

## Artifact observability

Persist bounded, non-reasoning data:

```text
experiment and code/dataset/topology/tool/prompt hashes
alert and observation window
role, turn, decision type, targets, tool summaries
evidence IDs visible to each role and bounded provenance summaries
draft, critique disposition, evidence gap, final structured hypothesis
terminal state and stop reason
calls, tools, duplicate suppression, tokens, latency, cost
all metric and safety counters
```

Persist submitted structured outputs, not private chain-of-thought or unlimited
telemetry. Evaluator-only truth remains in grader storage.

## Leakage audit

Allowed model-visible facts are production alert scope, bounded topology,
registered tools, truthful Evidence summaries, real historical changes, and
current state. Forbidden facts are evaluator scenario ID when not operationally
required, fixture name, expected component/mechanism/trigger, grader output,
and scenario-specific support predicates.

The current `FrozenIncident.public_context()` contains metadata for offline
tests, but the live path builds context from real Incident/Alert/evidence data.
That separation must remain explicit in v0.3 tests.

No MCP, A2A, vector memory, RAG, LangGraph, routing, fallback, or voting is
part of this first experiment. Explicit Python orchestration keeps architecture
effects separate from transport/framework effects.

## Pre-registered success criteria

Freeze before implementation and live calls:

1. Candidate C improves at least one primary causal behavior over the
   reconstructable v0.2 baseline: cross-component exploration above `0/1` or
   change-evidence acquisition above its observed `0/1` opportunity.
2. Canonical causal-component accuracy is reported; v0.2's 40% free-text
   service score is not relabeled as a semantic baseline.
3. Compatibility-set mechanism accuracy is at least `80%` and completion at
   least `90%`.
4. Submitted-hypothesis reference integrity remains `100%`.
5. Causal-evidence coverage and structured-trigger accuracy are reported under
   frozen definitions; no thresholds are chosen after results.
6. All safety gates remain zero/absent and all budgets/no-retry limits hold.
7. One-pass results are never selectively rerun. Any repeat plan is allocated
   before the first model call.

Failure means H1 is not supported under this contract; it does not authorize
post-result tuning.
