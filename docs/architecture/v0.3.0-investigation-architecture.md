# A1 improved single-agent architecture

Status: proposed control-arm design. This document does not implement v0.3.

## Architecture

```text
                    Incident + Alerts
                           |
                           v
                 Deterministic Runtime
                           |
                           v
                    Single Investigator
                           |
                           v
                  Typed Read-Only Tools
                           |
                           v
                 Runtime-Owned Evidence
                           |
                           v
              Structured Causal Hypothesis / STOP
```

A1 remains one model role. There is no Critic, Commander, specialized agent,
agent-to-agent bus, MCP or A2A transport.

## Authority boundary

| Area | Model may do | Runtime owns |
| --- | --- | --- |
| Investigation | select evidence, choose valid targets, interpret observations | tool implementation, execution and query bounds |
| Components | propose a causal component from known IDs | canonical component registry and topology truth |
| Evidence | cite existing IDs | creation, ownership, provenance and windows |
| Control | submit a hypothesis or STOP | budgets, deduplication, policy, validation and termination |
| Infrastructure | none | Kubernetes permissions, benchmark setup and all writes |

## Component model and topology

The A1 component model deliberately separates two identity domains:

```text
WorkloadComponentId     operational workload/service owner
DependencyResourceId    directly implicated infrastructure resource
```

Both are runtime-owned canonical identifiers derived from deployed topology,
not from frozen expected answers. The current source and manifests verify these
components and edges:

```text
order-service  -> payment-service  (HttpPaymentGateway)
order-service  -> postgresql       (order persistence)
order-service  -> kafka            (orders.created publisher)
payment-service -> postgresql      (payment persistence)
order-worker   -> kafka            (orders.created consumer)
order-worker   -> redis            (processed-event state)
```

The initial workload registry should cover `order-service`, `payment-service`
and `order-worker`. The initial dependency-resource registry should cover
`postgresql`, `kafka` and `redis`. Implementation must validate both registries
against deployed topology before freezing the A1 hashes; these values are not
derived from benchmark ground truth.

The model may receive a compact projection:

```json
{
  "components": ["order-service", "payment-service", "order-worker", "postgresql", "kafka", "redis"],
  "dependencies": [
    {"source": "order-service", "target": "payment-service"},
    {"source": "order-service", "target": "postgresql"},
    {"source": "order-service", "target": "kafka"},
    {"source": "payment-service", "target": "postgresql"},
    {"source": "order-worker", "target": "kafka"},
    {"source": "order-worker", "target": "redis"}
  ]
}
```

This is production architecture context. It must not contain a scenario ID,
fixture, expected component, expected mechanism, expected trigger, grader
predicate or instruction to inspect a particular dependency. Tool targets are
validated identifiers from the appropriate domain; arbitrary strings are
rejected.

## Symptom and causal ownership

A1 replaces the ambiguous primary use of `affected_component` with:

```text
symptom_component  = WorkloadComponentId owning the observed alert/symptom
causal_component   = WorkloadComponentId owning the causal behavior
causal_resource    = DependencyResourceId directly implicated, or null
```

The frozen dataset's `affected_component` is interpreted as the workload/service
owner of the operational cause, not as a database, broker or cache resource.
For example, database pressure may have `causal_component=payment-service` and
`causal_resource=postgresql`. A dependency incident may have different symptom
and causal workload components. Legacy v0.2 exact-string fields may be emitted
only as a compatibility projection and are not A1's primary component metric.

## Structured output contract

The proposed contracts are strict Pydantic models with `extra=forbid`, strict
types, bounded strings/lists and runtime-known enum values:

```text
CausalHypothesis
  symptom_component: WorkloadComponentId
  causal_component: WorkloadComponentId
  causal_resource: DependencyResourceId | None
  mechanism: HypothesisMechanism
  structured_trigger: StructuredTrigger
  causal_summary: string <= 1,000 characters
  evidence_ids: list[UUID] <= 12

StructuredTrigger
  trigger_type: TriggerType
  trigger_component: WorkloadComponentId
  trigger_resource: DependencyResourceId | None
  signal: TriggerSignal

StopDecision
  stop_reason: StopReason
  considered_components: list[WorkloadComponentId] <= 8
  missing_evidence_categories: list[EvidenceCategory] <= 8
```

The final trigger vocabulary is frozen before A1 implementation/live use. It
must represent the current causal concepts without being derived from fixture
names: error-rate increase, service latency, dependency latency, database
connection pressure, database query latency, consumer lag, consumer failure,
pod restart and configuration change. `causal_summary` is human-readable and
reported separately from the deterministic structured score.

## Bounded protocol

```text
TURN 1  initial symptom investigation
TURN 2  causal discrimination and bounded expansion
TURN 3  structured hypothesis or structured STOP only
```

Context contains current turn, remaining model/tool budget, the production
symptom component, topology, registered tools, runtime evidence and components
already queried. It never contains the frozen causal answer. The runtime records
`components_queried_by_turn` from validated tool arguments, for example:

```json
{"1": ["order-service"], "2": ["payment-service"]}
```

The runtime also records unique components, outside-alert-scope executions,
outside-scope component count and change-tool requests. These are behavior
metrics, not hidden evaluator labels.

## Evidence and audit

All future roles would share one incident-owned evidence store; for A1 there is
only one role. Every Evidence record must persist bounded provenance:

```text
evidence_id
tool
target_component
source_system
temporal_mode
observation_window
bounded_observation_summary
collected_at
```

The model cannot create Evidence. The runtime validates that every submitted ID
belongs to the current incident. A1's primary integrity metric is:

```text
submitted hypotheses with all runtime-owned current-incident references
/ submitted hypotheses
```

Evidence targeting the claimed causal component can support an internal
provenance metric, but target match alone is not semantic proof of causality.

## Safety invariants

Hard floors for A1 are:

```text
fabricated evidence accepted = 0
cross-incident evidence accepted = 0
agent infrastructure writes = 0
Kubernetes write verbs = 0
arbitrary shell = absent
arbitrary kubectl = absent
autonomous remediation = absent
```

All roles in any future A2 treatment must inherit these same runtime
boundaries. A1 does not implement remediation.
