# v0.3.0 Investigation Architecture

Status: proposed architecture for the first v0.3 experiment. This document
does not implement the runtime.

## Decision

The first v0.3 experiment will test **Investigator + Critic** as two bounded
model roles behind the existing deterministic runtime. The roles communicate
only through strict typed contracts and remain in-process. This is a minimal
multi-role experiment, not an agent swarm.

The runtime remains the sole authority for:

```text
registry and schemas
tool execution and query bounds
evidence creation and ownership
observation windows and deduplication
incident scope and budgets
sequencing and termination
Kubernetes permissions and writes
benchmark setup and cleanup
```

## Why this architecture

The v0.2 evidence supports two concrete experiments:

1. V020-003 stayed on `order-service` despite a frozen causal component of
   `payment-service`.
2. V020-010 did not acquire an available configuration-change observation.

Candidate A can test structured causal fields and explicit exploration, but it
does not independently test whether a challenge step improves attribution.
Candidate B can enforce deterministic policy checks, but cannot know causal
ownership at runtime without importing evaluator truth. Candidate D adds role
complexity not justified by one clear cross-component case and one acquisition
miss. Candidate C is the smallest candidate that directly tests evidence
gathering, causal exploration, and evidence challenge.

This is a falsifiable experiment choice, not a claim that multi-agent systems
are inherently better or required.

Because Candidate C is selected, the proposed milestone name remains
`v0.3.0 — Evidence-Grounded Multi-Agent Investigation`. It describes this
bounded two-role experiment, not a production claim or a specialized-agent
swarm.

## Role boundaries

### Investigator

The Investigator receives alert/incident facts, bounded production topology,
the read-only catalog, and runtime-owned evidence. It may select safe tools,
identify symptom and candidate causal components, and submit a bounded draft.
It may not create evidence, expand budgets, change policy, or execute writes.

### Critic

The Critic receives the same incident context, bounded evidence projection,
topology, and structured draft. It may accept, reject unsupported attribution,
or request a typed evidence gap. It may not create or edit evidence, execute
tools directly, expand budgets, or see evaluator expected answers.

### Deterministic runtime

The runtime validates every response, checks evidence ownership, resolves
components/categories against registered topology and tools, executes only
read-only work, shares the global tool budget, suppresses reusable duplicates,
and owns final termination.

All roles share one incident-owned evidence repository and one duplicate
identity/history. No role receives remediation authority.

## Typed protocol

Proposed strict Pydantic contracts use `extra=forbid`, bounded lengths/lists,
and no free-form agent-to-agent chat:

```text
ComponentId
  value: runtime-known canonical component identifier

InvestigationPlan
  symptom_component: ComponentId
  candidate_components: list[ComponentId] <= 8
  requested_tools: list[ToolRequestSpec] <= 8

DraftHypothesis / FinalHypothesis
  symptom_component: ComponentId
  causal_component: ComponentId
  mechanism: HypothesisMechanism
  structured_trigger: StructuredTrigger
  causal_summary: str <= 1,000 chars
  evidence_ids: list[UUID] <= 12

Critique
  disposition: ACCEPT | REQUEST_EVIDENCE | REJECT_UNSUPPORTED
  challenged_fields: list[CritiqueField] <= 4
  missing_evidence: list[EvidenceGapRequest] <= 3
  referenced_evidence_ids: list[UUID] <= 12

EvidenceGapRequest
  target_component: ComponentId
  evidence_category: EvidenceCategory
  rationale_code: RationaleCode
```

The exact enum members and bounds are frozen before implementation. No
contract carries evaluator answers or arbitrary query language.

## State machine and bounds

```text
START -> INVESTIGATE -> DRAFT_READY -> CRITIQUE

CRITIQUE -> FINALIZE       ACCEPT
CRITIQUE -> EVIDENCE_GAP   REQUEST_EVIDENCE
CRITIQUE -> STOP           REJECT_UNSUPPORTED or invalid response

EVIDENCE_GAP -> FOLLOW_UP  runtime executes validated gap
EVIDENCE_GAP -> STOP       authority or budget failure

FOLLOW_UP -> FINALIZE       one terminal FinalHypothesis
FOLLOW_UP -> STOP           explicit insufficient evidence
```

The initial Investigator phase allows at most two model calls. The Critic allows
one call. A validated gap is executed by the runtime, followed by at most one
terminal Investigator call. The first experiment therefore freezes:

```text
max model calls / incident: 4
max actual tool executions / incident: 8
provider retries: 0
```

If the Critic accepts, the draft is finalized without another model call. A
follow-up response cannot request another tool batch. There is no open-ended
cycle or retry loop.

## Evidence-gap translation

The Critic requests a target component, evidence category, and rationale code,
not an arbitrary tool. The runtime validates the target against topology,
maps the category only to supported registered read-only tools, applies the
authoritative incident window, and shares deduplication with prior work.

This is less expressive than direct tool selection but gives the runtime a
smaller authority surface. The Investigator retains normal v0.2-style tool
selection for initial exploration.

## Components and topology

The current workload code establishes these edges:

```text
order-service -> payment-service   (HTTP payment gateway)
order-service -> postgresql        (order persistence)
order-service -> kafka             (orders.created publisher)
payment-service -> postgresql      (payment persistence)
order-worker -> kafka              (orders.created consumer)
order-worker -> redis              (processed-event state)
```

The canonical v0.3 component registry should be derived from deployed topology
and versioned with it. Candidate identifiers include the six verified workload
and dependency components above. `symptom_component` is the alert/symptom
owner; `causal_component` is the structured RCA owner. They are scored
separately.

The topology may be model-visible as bounded production context. A fact such as
`order-service depends on payment-service` is valid operational knowledge, not
an answer key. Runtime still validates every target and the context must not
contain expected causal components, mechanisms, triggers, fixture names,
grader output, or scenario-specific support predicates.

## Structured trigger

Future primary scoring uses:

```text
StructuredTrigger
  type: TriggerType
  component: ComponentId
  signal: TriggerSignal
```

Candidate causal classes are error-rate increase, dependency latency, database
connection pressure, database query latency, consumer stall, consumer failure,
pod restart, and configuration change. The final vocabulary is frozen before
any live run and is not derived from individual fixture names. A bounded
human-readable `causal_summary` is reported separately.

## Shared evidence and safety

Investigator and Critic project one runtime-owned EvidenceRepository. Evidence
IDs retain source, tool, target, temporal mode, query interval, and collection
metadata. A Critic cannot cause an identical fixed-window query to execute
again. Current-state refresh follows the existing repeat policy.

Invalid role responses, unknown components, unsupported categories, fabricated
references, and budget overflow fail closed. All roles retain:

```text
fabricated evidence accepted = 0
cross-incident evidence accepted = 0
agent infrastructure writes = 0
Kubernetes write verbs = 0
arbitrary shell = absent
arbitrary kubectl = absent
autonomous remediation = absent
```

No MCP, A2A, vector memory, RAG, LangGraph, routing, fallback, or voting is
part of this first experiment. In-process typed orchestration keeps architecture
effects separate from transport/framework effects.

## Comparison and extension scope

The primary paid comparison is Candidate C against the frozen v0.2 baseline on
the original ten compatibility scenarios, one run each. Fault definitions,
telemetry, Alertmanager ingestion, tool semantics, evidence authority, model
family/configuration where available (`gpt-5.6-luna`, reasoning `none`), and
grader ground truth remain fixed.

Future extension cases must be frozen before use and should cover:

```text
upstream dependency latency
downstream dependency failure
database-induced downstream symptom
Kafka-induced worker symptom
configuration change causing another component's symptom
shared-dependency ambiguity
```

They are not implemented here and cannot rewrite v0.2 results.

## Artifact requirements

Future runs persist bounded non-reasoning data: experiment and topology hashes;
alert and observation window; role/turn/decision; target components and tool
summaries; evidence IDs visible to each role; bounded evidence provenance;
draft, critique, gap, and final structured outputs; terminal state; calls,
tools, tokens, latency, cost, and safety counters. Private chain-of-thought and
unlimited logs/traces are never persisted.
